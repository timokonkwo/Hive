# HIVE claim checker

Current budget: **10M new HIVE total**, increased by the user after the original 7M review. Earlier 7M figures below are historical. The current checker, campaign inputs and 10M preview artifacts use the revised budget; funding has not been verified.

Current implementation and operating instructions: **`HIVE_CLAIM_HANDOFF.md`**. The checker, injected-wallet UI, same-origin API proxy, persistent operator gateway and deposit/status integration are now implemented locally. Claims remain disabled. The sections below also record earlier implementation stages; statements that wallet integration was pending describe those earlier stages.

Local route: `/token/claim`. Lookup endpoint: `GET /api/token/claim?owner=<public Solana address>`. The HIVE page links directly to the checker. The former `/token/reimbursement` and `/api/token/reimbursement` routes are absent; no redirects were added.

The public snapshot extract is generated by `node tools/hive-migration/export-checker-snapshot.mjs`, which checks the original holder JSON SHA-256 before exporting only owner, exact balance and wallet/pool/custody classification. It excludes internal staking records, token-account lists and destination links. The application validates cutoff identity, totals, unique owners and classifications. Raw amounts use integer strings throughout.

Ordinary snapshot wallets see an explicitly provisional estimate using the selected proportional 7M budget and 70% cap. Custody and pool addresses receive their separate review/exclusion states without a wallet estimate. Missing addresses are distinguished from lookup failures. Final allocation, required surrender and deadlines remain pending; no wallet connection, signature, deposit or payout is implemented by this checker.

Current balances are read server-side using only `getGenesisHash` and `getTokenAccountsByOwner`, mainnet identity, finalized commitment and a minimum context slot. Unfrozen accounts are summed exactly. Wrong-chain, stale, malformed, duplicated and unavailable data fail to an unknown balance, never zero. RPC credentials remain on the server. Reads have five-second timeouts; the route uses the existing per-process rate limiter and private/no-store responses. Distributed rate limiting remains a production infrastructure consideration.

Validation: production build, TypeScript, scoped ESLint, 17 focused claim/token tests and 22 Chrome browser checks passed. Browser coverage includes ordinary, custody, pool, absent, invalid and offline states; 375/768/1280px in light and dark themes; clearing old results when editing and the link from `/token`. A local production API lookup successfully read finalized Solana slot 449450351 on 22 September 2026. This is a balance observation, not financial execution.

No push, deployment, public announcement or transaction occurred. Final eligibility/custody, funding, dates and deployed settlement integration remain in `HIVE_REIMBURSEMENT_INPUTS.md`.

## Migration review and compact amounts

The checker now displays K/M amounts with at most one decimal (50.2K, 40M), omitting trailing `.0`. Exact integer amounts remain unchanged in all allocation arithmetic; the review's optional exact-amount disclosure preserves precision. Tiny nonzero quantities display `<0.1` rather than zero.

Ordinary snapshot wallets can choose **Review migration**. This rereads the snapshot and finalized current holdings before opening an inline review. The deposit preview is capped by both snapshot and spendable holdings; the estimated new-HIVE amount is calculated from that capped amount. Zero holdings and unavailable balances have explicit states. Lower balances are allowed as partial deposits and receive the same proportional rate on the old HIVE actually surrendered. Pool, absent and unresolved custody addresses cannot enter the ordinary wallet review.

The review explains wallet ownership proof, escrow deposit, reserved payout and new-HIVE receipt. **Deposit & claim remains disabled**: deployed program/distributor addresses, funding, final eligibility, dates and claim policy are missing. No financial activation, live reservation, wallet signature or transaction is represented as implemented by the public checker. The local verifier/contract tooling remains separate pending deployed integration.

## Signed request intake preparation

The operator-side intake is now implemented in `tools/hive-migration/escrow/accept-registration.mjs`. It authenticates both wallets, rejects stale/unapproved requests and atomically queues only the signed fields. Concurrent identical submissions are idempotent; competing registrations cannot overwrite the original claim. Three focused intake tests cover these cases. This is a local operator interface, not a live public submission endpoint.

Still required for an executable migration: final owner selection; reviewed dates/terminal-attempt terms; paused deployments, funded inventory and deployment verification; wallet UI and durable public-to-operator transport; an end-to-end deployed rehearsal and explicit activation. None of those missing inputs were inferred from the collection wallet or historical launch wallets.

## Review and partial amount selection  -  22 September 2026

Fixed two checker integrity gaps: the server now pins the full public snapshot content hash (verified against the original export), detecting balance changes even when aggregate totals stay the same; the UI now validates response states, integer amounts, balance metadata and proportional estimates before rendering. These affect the provisional checker, not the separately reviewed on-chain Merkle tree.

The migration review now accepts a chosen partial amount and offers Use maximum. Input is parsed with integer arithmetic, rejects K/M, scientific notation, excess precision, zero and values above the available snapshot balance. Displayed totals retain one-decimal K/M formatting. The preview discloses the current V1 restriction: one deposit per wallet, with no later top-up. This restriction still needs final campaign approval.
